# API reference

OpenAPI generated by FastAPI is authoritative at `/docs`. This document explains the workflow contracts and trust boundary; it intentionally omits internal implementation details.

## Conventions

- Public prefix: `/api/v1`
- JSON content type: `application/json`
- IDs are opaque strings.
- Timestamps are UTC ISO 8601.
- List endpoints return `{items, total, next_cursor}`.
- Errors return a stable code, safe message, retryable flag, correlation ID, and optional details.
- Internal endpoints require `X-Internal-Token` and are never called by the browser.

## Public workflow ingress

### POST /api/v1/runs/support

~~~json
{
  "ticket_id": "T-1003",
  "customer_id": "CUST-1002",
  "subject": "Stolen card",
  "message": "Customer CUST-1002 says their card is stolen. What should we do?",
  "correlation_id": "demo-stolen-card"
}
~~~

Creates an execution, sends its envelope through `support-triage` in n8n when orchestration is enabled, and returns the authoritative execution object.

### POST /api/v1/runs/invoice

~~~json
{
  "document_name": "INV-2026-1002.txt",
  "document_content": "Invoice Number: INV-2026-1002\\nVendor: Elbe Systems AG\\nInvoice Date: 2026-08-21\\nSubtotal: 1000.00\\nTax: 190.00\\nTotal: 1210.00\\nCurrency: EUR"
}
~~~

`extracted_fields` may be supplied in deterministic test fixtures; production-like input uses document content. Validation decisions never come from the model.

### POST /api/v1/runs/incident

~~~json
{
  "source": "monitoring",
  "service": "payments-api",
  "severity": "critical",
  "events": ["latency > 3s", "HTTP 5xx spike", "database connection failures"]
}
~~~

The domain service normalizes a fingerprint, deduplicates within the configured window, validates a hypothesis-safe summary, and performs idempotent Jira/Slack mock actions.

## n8n internal run contract

n8n receives this envelope from public ingress:

~~~json
{
  "execution_id": "opaque-id",
  "correlation_id": "corr-demo",
  "workflow": "support",
  "payload": {
    "ticket_id": "T-1003",
    "customer_id": "CUST-1002",
    "subject": "Stolen card",
    "message": "Customer CUST-1002 says their card is stolen. What should we do?"
  }
}
~~~

It forwards the same envelope to exactly one protected endpoint:

- `POST /api/v1/internal/runs/support`
- `POST /api/v1/internal/runs/invoice`
- `POST /api/v1/internal/runs/incident`

This resumes the existing execution. It does not create another one, so retries are safe and cannot recurse through the public ingress.

## Shared AI operations

| Method and path | Purpose |
|---|---|
| `POST /api/v1/ai/classify` | Strict category, risk, confidence, reason, human flag |
| `POST /api/v1/ai/summarize` | Structured incident-safe summary |
| `POST /api/v1/ai/extract` | Strict invoice extraction |
| `POST /api/v1/ai/generate-response` | Grounded readable support draft |

Provider output is parsed into Pydantic models. Malformed output is repaired at most once; raw malformed content is not returned to operators.

## Execution and observation

| Method and path | Purpose |
|---|---|
| `POST /api/v1/executions` | Create a low-level execution record |
| `GET /api/v1/executions` | Newest-first execution list |
| `GET /api/v1/executions/{id}` | Full state, timeline, approvals, AI calls, actions, audits |
| `GET /api/v1/executions/{id}/events` | Ordered stage events |
| `GET /api/v1/metrics` | Numeric totals, rates, average and p95 latency |
| `GET /api/v1/health` | Application health alias |
| `GET /health` | Liveness |
| `GET /ready` | Database-aware readiness |

Execution statuses are `received`, `running`, `waiting_for_review`, `completed`, `completed_with_warning`, `failed`, and `cancelled`.

## Human approval

| Method and path | Purpose |
|---|---|
| `POST /api/v1/approvals` | Create an approval item |
| `GET /api/v1/approvals` | Pending newest-first by default |
| `GET /api/v1/approvals/{id}` | Context, original input, timeline and decisions |
| `POST /api/v1/approvals/{id}/approve` | Approve through a deterministic side-effect gate |
| `POST /api/v1/approvals/{id}/reject` | Cancel without executing a side effect |

Decision body:

~~~json
{
  "reviewer": "demo.operator",
  "note": "Verified through the demo review procedure."
}
~~~

A rejected item never invokes CRM or ERP. Approving an invalid invoice acknowledges the review but deterministic validation still blocks ERP submission.

## Audit

- `POST /api/v1/audit/events` - protected orchestration write
- `GET /api/v1/audit/events` - filtered/newest-first audit list

n8n write body:

~~~json
{
  "execution_id": "opaque-id",
  "event_type": "n8n.support.waiting_for_review",
  "actor": "n8n",
  "summary": "High-risk support request requires mandatory review.",
  "details": {"n8n_execution_id": "42", "workflow": "support"}
}
~~~

## Local mock systems

| Method and path | Behavior |
|---|---|
| `POST /mock/crm/tickets` | Allowlisted response/escalation/note |
| `GET /mock/crm/tickets` | Persisted CRM actions |
| `POST /mock/erp/invoices` | Idempotent validated invoice insertion |
| `GET /mock/erp/invoices` | Persisted ERP invoices |
| `POST /mock/jira/issues` | Idempotent incident creation |
| `GET /mock/jira/issues` | Persisted incidents and occurrences |
| `POST /mock/slack/messages` | Idempotent incident notification |
| `GET /mock/slack/messages` | Persisted messages |

Mock records carry the originating execution ID.

## Demo catalogue

- `GET /api/v1/demo/scenarios` lists synthetic scenarios.
- `POST /api/v1/demo/scenarios/{id}/run` runs a scenario through the same public orchestration path.

The canonical data also lives under [fixtures](../fixtures/) for inspection and external probes.

## Fault profiles

The local demo accepts only predefined fault profiles: `provider_timeout_once`, `provider_malformed_once`, `provider_malformed_twice`, `crm_failure`, `erp_failure`, `jira_failure`, and `slack_failure_once`. Arbitrary fault commands, URLs, and shell input are not accepted.
